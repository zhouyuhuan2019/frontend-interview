RAG 的检索质量很大程度由「怎么把文本变成向量」和「用哪套检索库」决定，这两点是面试的区分点。

## 参考答案

**向量嵌入（Embedding）**：把文本/图片映射到高维空间中的一个稠密向量，让**语义相近的内容在空间里距离也近**。它是嵌入模型训练出来的，不是简单的特征拼接。

**相似度度量**：

| 度量 | 公式直觉 | 特点 |
| --- | --- | --- |
| 余弦相似度 | 看两个向量的夹角 | 只看方向、忽略长度，最常用于文本 |
| 点积 | 方向 × 长度 | 向量已归一化时等价于余弦，且更快 |
| 欧氏距离 | 两点直线距离 | 对向量长度敏感，未归一化时易失真 |

**向量数据库选型**：

| 方案 | 定位 | 适合场景 |
| --- | --- | --- |
| pgvector | 关系库扩展 | 已有 Postgres，想少引入组件 |
| Chroma / FAISS | 轻量库 | 本地开发、小规模原型 |
| Qdrant / Milvus | 专用向量库 | 中大规模、要高吞吐与元数据过滤 |
| Pinecone 等云服务 | 全托管 | 不想运维、追求开箱即用 |
| Elasticsearch / OpenSearch | 搜索引擎 | 已用 ES，想复用全文 + 向量混合检索 |

一句话：**小规模能省就省（pgvector / Chroma），中大规模选专用向量库（Milvus / Qdrant），不想运维就上云。**

## 原理讲解

嵌入模型通常在「语义相似的两句话要靠近、无关的要远离」这类对比学习目标下训练，因此不同表达但同义的内容，输出向量夹角很小——这就是语义检索的基础。

**为什么常把向量归一化？** 归一化后每个向量长度为 1，此时**点积 = 余弦相似度**，而点积计算更快、更易被硬件加速。很多向量库默认对向量做归一化。

下面演示：同一个查询向量，与三个候选分别算余弦、欧氏距离和归一化点积。

```js run
const query = [0.6, 0.8]
const items = [
  { name: 'A', vec: [1.2, 1.6] }, // 与 query 同方向，但更长
  { name: 'B', vec: [0.6, 0.8] }, // 与 query 完全相同
  { name: 'C', vec: [0.8, 0.6] }, // 方向接近、长度相同
]

const norm = (v) => {
  const len = Math.sqrt(v.reduce((s, x) => s + x * x, 0))
  return v.map((x) => x / len)
}
const dot = (a, b) => a.reduce((s, x, i) => s + x * b[i], 0)
const cosine = (a, b) => dot(norm(a), norm(b))
const euclid = (a, b) => Math.sqrt(a.reduce((s, x, i) => s + (x - b[i]) ** 2, 0))

for (const it of items) {
  console.log(
    `${it.name}  cosine=${cosine(query, it.vec).toFixed(3)}  ` +
      `euclid=${euclid(query, it.vec).toFixed(3)}  ` +
      `dot(norm)=${dot(norm(query), norm(it.vec)).toFixed(3)}`,
  )
}
```

```text output
A  cosine=1.000  euclid=1.000  dot(norm)=1.000
B  cosine=1.000  euclid=0.000  dot(norm)=1.000
C  cosine=0.960  euclid=0.283  dot(norm)=0.960
```

A 与 query 方向完全相同（语义相同），余弦给出满分 1.0，但欧氏距离因「长度差」给了 1.0——**这就是余弦更抗长度干扰、更适合文本的原因**。归一化点积的结果与余弦完全一致，印证了三者关系。

**检索算法**：精确检索要逐个算距离，复杂度 O(N)；生产中多用**近似最近邻（ANN）**：

- **HNSW**：分层图，查询快、召回高，是多数向量库的默认索引，代价是内存占用大；
- **IVF**：先聚类分桶，只搜少数桶，省内存、精度略低；
- 还有 **PQ 量化**压缩向量，进一步降内存。

## 追问与易错点

- **建库和查询必须用同一个模型吗？** 必须。不同模型产出的向量空间不互通，换了嵌入模型就要**全量重建索引**。
- **维度越高越好吗？** 不是。高维表达力强但存储和计算更贵，且有边际递减；不少模型支持 Matryoshka 截断维度，可在少量精度损失下省成本。
- **向量库能替代全文搜索吗？** 不能。向量擅长语义、弱于精确匹配（型号、人名、编号）；最佳实践是**混合检索**：向量 + BM25 关键词。
- **「相似」在业务里一定相关吗？** 不一定。向量是语义相近，业务相关性还要靠 Rerank、元数据过滤和规则兜底。
- **ANN 会漏掉正确结果吗？** 会。近似检索用召回率换速度，可用「先粗查再用精确距离 Rerank」降低漏检。
