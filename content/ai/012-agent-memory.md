你负责一个有长期陪伴属性的 AI 助手，用户希望它「记住我」。记忆系统你会怎么设计？

## 参考答案

Agent 的「记忆」不是一个东西，而是**按生命周期分层的四类存储**，设计的关键是「什么进上下文、什么落盘、什么被检索回来」。

| 层 | 存什么 | 载体 | 生命周期 |
| --- | --- | --- | --- |
| 工作记忆 | 当前任务的即时状态（工具调用中间结果） | 上下文窗口 | 单次请求 |
| 短期记忆 | 当次会话的历史消息 | 消息列表（可压缩） | 单次会话 |
| 长期记忆 | 跨会话的用户画像、偏好、事实结论 | 向量库 + 结构化表 | 持久 |
| 外部知识 | 公共领域知识 | RAG / 向量库 | 持久（与用户无关） |

一句话：**短期记忆 = 上下文窗口管理，长期记忆 = 抽取 + 存储 + 检索**。二者最容易踩的坑分别是「窗口溢出」和「检索回来一堆噪声」。

## 原理讲解

**1. 短期记忆：本质是上下文窗口管理**

上下文窗口是有限的（且窗口越大越贵、注意力越稀释），会话一长就必须压缩。常用策略组合：

- **滑窗**：只保留最近 N 轮对话，简单但会丢早期关键信息；
- **滚动摘要**：让模型把较早的对话摘要成一段「会话纪要」替换原文，保留语义、压缩 token；
- **结构化抽取**：把「用户叫张三」「在学 Vue3」这类稳定事实抽成结构化字段单独存，不再占用对话历史；
- **token 预算**：给系统提示、摘要、最近对话、工具结果分配固定额度，超了先砍工具结果、再砍旧对话。

```text
预算分配示例（窗口 128k）
├─ 系统提示 / 工具定义    ~5k
├─ 长期记忆检索结果       ~2k
├─ 滚动摘要              ~4k
├─ 最近 N 轮原始对话      ~剩余
└─ 预留输出空间           ~16k
```

**2. 长期记忆：抽取 → 存储 → 检索 三步**

- **写入（Extraction）**：不是把整段对话存进去，而是从对话中**抽取值得记的事实/偏好/结论**（「用户对花生过敏」「本项目用 pnpm」），转成文本后 embedding 存入向量库（pgvector / Milvus / Qdrant），或按字段存入结构化表；
- **检索（Retrieval）**：新对话开始时，用当前 query 去向量库召回相关记忆，注入系统提示。打分通常综合 **相似度 + 新近度（recency）+ 重要度（importance）**，避免旧记忆压过新偏好；
- **更新与遗忘**：同一事实的新记忆要能覆盖旧记忆（冲突消解），过期信息设 TTL 或定期衰减；去重避免同一事实存几十条。

**3. 记忆 vs RAG**

两者都基于向量检索，但定位不同：**RAG 检索的是「公共知识」，对所有用户一样；记忆是「关于这个用户/这个会话的私有信息」**，必须按 `user_id` / `tenant` 严格隔离，否则就是严重的越权与隐私事故。

**4. 工程落地分工**

Agent 编排层（后端）负责记忆的读写与检索；前端通常只需：持久 `sessionId`（放 localStorage/内存，注意隐私与登出清理）、渲染「正在回忆……」等状态、提供「清空记忆」入口。别把带隐私的记忆明文长期丢在前端本地存储。

## 追问与易错点

- **上下文窗口不够用，直接换更大窗口行不行？** 治标不治本：成本线性上升、延迟增加，还有「lost in the middle」——长上下文中间的信息最易被忽略。压缩和检索才是正解。
- **记忆写错了（幻觉记忆）怎么办？** 写入前加置信度/校验，允许用户纠正，冲突时以最新确认为准；把「记忆」当软提示而非硬事实。
- **长期记忆如何防止用户串号？** 按 `user_id/tenant` 做 namespace 隔离，检索时必须带隔离条件，绝不跨租户。
- **记忆和 RAG 是一回事吗？** 不是，机制相似但语义不同：一个是「我了解你的信息」，一个是「世界上的知识」。
- **什么时候不该用记忆？** 一次性任务、强合规场景（金融/医疗）默认不持久化，避免隐私与合规风险。
