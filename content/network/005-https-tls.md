## 参考答案

HTTPS = HTTP + TLS，用三件武器解决三大问题：

| 目标 | 手段 |
| --- | --- |
| 防窃听 | **混合加密**：非对称加密交换会话密钥，之后用对称加密传输数据 |
| 防篡改 | 消息摘要 / MAC 校验，数据被改动即可发现 |
| 防冒充 | CA 签发的**数字证书**，证明「公钥确实属于这个网站」 |

**TLS 1.2 握手流程（2-RTT）**：

1. **ClientHello**：客户端发送支持的 TLS 版本、加密套件列表、客户端随机数。
2. **ServerHello + Certificate**：服务器选定加密套件、返回服务器随机数和**数字证书**。
3. 客户端**验证证书**（CA 签名、有效期、域名），生成「预主密钥」，用证书里的公钥加密后发给服务器。
4. 双方用两个随机数 + 预主密钥各自算出相同的**会话密钥**，互发 Finished，握手完成，之后全部走对称加密。

```text
客户端 ──ClientHello──────────────► 服务器
客户端 ◄─ServerHello+Certificate─── 服务器
客户端 ──预主密钥(公钥加密)+Finished─► 服务器
客户端 ◄─Finished────────────────── 服务器
        ── 之后：对称加密传输应用数据 ──
```

## 原理讲解

**为什么是混合加密？** 对称加密（AES）快但密钥没法安全地当面交给对方；非对称加密（RSA/ECDHE）可以公开公钥、私钥解密，安全但慢几个数量级。所以用非对称加密「保护密钥的交换」，用对称加密「保护海量业务数据」，各取所长。

**证书为什么能防中间人？** 中间人完全可以截获通信并伪造一对公私钥，但它伪造不了**证书的 CA 签名**——浏览器内置了可信根 CA 列表，验证时会沿证书链逐级验签：根 CA → 中间 CA → 站点证书，任何一环对不上都会失败。浏览器还会额外核对域名是否匹配、证书是否在有效期、是否已被吊销（OCSP）。中间人没有 CA 私钥，签不出能通过校验的证书，浏览器就会弹出「证书不受信任」的警告。这正是 Charles/Fiddler 抓包必须先**安装并信任它的根证书**的原因——相当于你亲手授权它当中间人。

**会话密钥的诞生**：两次握手交换了「客户端随机数 + 服务器随机数 + 预主密钥」三个材料，双方本地用相同算法算出主密钥，再派生出会话密钥。密钥本身从不直接在网络上传输（RSA 模式下是加密传输，ECDHE 模式下双方各自计算），即使后续被截获密文也无法还原。

**TLS 1.3 的改进**：

- 握手从 2-RTT 压缩到 **1-RTT**（ClientHello 直接带上密钥协商参数），会话恢复场景支持 **0-RTT**；
- 废弃了不安全的 RSA 密钥交换和一批老旧算法，强制前向安全（每次会话密钥独立，长期私钥泄露也不影响历史会话）。

## 追问与易错点

- **HTTPS 就绝对安全吗？** 不是。它只保护传输链路。XSS 偷数据、用户主动信任伪造证书、服务器本身被攻破，都不在 HTTPS 的保护范围内。
- **为什么抓包工具能看到 HTTPS 明文？** 因为你在本机安装并信任了它的根证书，它以「受信任的中间人」身份分别与浏览器和服务器建立两条 TLS 连接。
- **对称密钥会不会被算出来？** 会话密钥每次握手重新生成且很短命，配合前向安全的密钥交换算法（ECDHE），暴力破解在算力上不可行。
- **证书过期/域名不匹配会怎样？** 浏览器校验失败，直接拦截并给出警告页面，用户可以手动忽略但风险自负。
- **HTTPS 对性能影响大吗？** 主要成本在握手 RTT，可通过 TLS 1.3、会话复用（Session Ticket）、HTTP/2 复用连接等手段摊薄，现代站点开销已很小。
