## 参考答案

**HTTP/1.1 的痛点**：一个 TCP 连接同一时刻只能处理一对请求-响应（应用层队头阻塞），浏览器只能开 6~8 个并发连接；文本协议解析开销大、头部字段大量重复。

**HTTP/2 的四大改进**：

1. **二进制分帧**：数据被拆成带流 ID 的二进制帧，替代文本报文；
2. **多路复用**：同一连接上多个流的帧交错传输、并行收发，彻底解决**应用层**队头阻塞；
3. **HPACK 头部压缩**：静态表 + 动态表 + 哈夫曼编码，重复的头部只传索引；
4. **服务器推送 + 流优先级**：服务器可主动推送关联资源，浏览器可声明资源优先级。

**但 HTTP/2 仍有一个死穴**：多路复用建立在同一条 TCP 连接上，一旦发生丢包，TCP 的重传机制会让**所有流一起等待**——TCP 层的队头阻塞没解决。

**HTTP/3 = HTTP over QUIC（基于 UDP）**：

- QUIC 在**传输层**就实现了流的概念，某个流丢包只阻塞自己，**根治队头阻塞**；
- 握手内置 TLS 1.3，常规 1-RTT、会话恢复 **0-RTT**；
- **连接迁移**：用连接 ID 标识连接，Wi-Fi 切蜂窝网络 IP 变了连接也不断。

## 原理讲解

HTTP/2 把「请求」拆成了逻辑上的**流（Stream）**，每个流有唯一 ID，帧交错到达后按 ID 重新组装：

```text
HTTP/1.1：请求A ────► 响应A ────► 请求B ────► 响应B   （串行）
HTTP/2  ：帧A1 帧B1 帧A2 帧B2 帧A3 帧B3 …             （单连接交错）
```

这样域名分片、雪碧图、资源内联这些 HTTP/1.1 时代的优化技巧在 HTTP/2 下反而成了反模式（内联资源无法独立缓存，合并文件破坏按需加载）。

**为什么丢包对 HTTP/2 更伤？** 一个 TCP 连接的丢包重传期间，后续已到达的数据也不能向上交付。HTTP/1.1 下只有这一个请求被卡，HTTP/2 下单连接上几十个流被一起卡——高丢包率的弱网环境里，HTTP/2 可能比 HTTP/1.1 还慢。这正是 QUIC 要把流独立下放到传输层的原因。

**QUIC 的连接迁移**：TCP 用「源 IP + 源端口 + 目的 IP + 目的端口」四元组标识连接，手机切个网络连接就断了；QUIC 用一个随机连接 ID，四元组怎么变都能续上，对移动端体验提升巨大。

## 追问与易错点

- **HTTP/2 必须配 HTTPS 吗？** 协议规范没强制，但主流浏览器只实现了 TLS 之上的 HTTP/2，事实标准就是必须。
- **有了多路复用，还需要减少 HTTP 请求吗？** 仍然需要控制总量（每个请求都有处理开销），但不用再为「绕开连接数限制」做合并雪碧图这类极端优化。
- **服务器推送为什么被弃用？** 推送策略难以和浏览器缓存协调，常常推了浏览器已有的资源浪费带宽，Chrome 已移除支持，实践中用 `103 Early Hints` 或 preload 替代。
- **HTTP/3 普及的障碍？** UDP 可能被企业防火墙拦、服务端中间件支持仍在演进，所以主流方案是 HTTP/3 + HTTP/2 双栈回退（通过 Alt-Svc 头协商）。
- **0-RTT 有安全风险吗？** 有重放攻击风险，只应用于幂等请求。
