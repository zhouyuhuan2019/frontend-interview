先看下面这个列表，思考：在**头部插入**一条新数据时，用 `index` 和用 `id` 做 key 分别会发生什么？

```jsx
function TodoList({ todos }) {
  return (
    <ul>
      {todos.map((todo, index) => (
        // 写法一：key={index}   写法二：key={todo.id}
        <li key={todo.id}>
          <input defaultValue={todo.text} />
        </li>
      ))}
    </ul>
  )
}
```

## 参考答案

key 的作用：在**调和（reconciliation）**过程中帮助 React 识别「哪个元素还是哪个元素」，从而决定 DOM 节点和组件状态是**复用、移动还是重建**。

不写 key 时，React 默认按**下标顺序**逐个对比，等价于 `key={index}`。

用 index 当 key 的三大问题：

1. **状态错乱**：组件实例按位置复用。头部插入后，原来的第 1 项变成了第 2 项，但它的 state、非受控输入（如上面的 `defaultValue`）还留在原位，视觉上数据「串行」；
2. **多余的 DOM 操作**：头部插入一个元素，React 认为从位置 0 开始每一项内容都变了，逐个原地更新，而不是「插入一个 + 其余不动」；
3. **排序 / 删除同样中招**：凡是会改变元素位置的操作，index 都会让节点身份错位。

用稳定唯一的 `id` 做 key 后，React 能识别出「老节点只是往后挪了」，只做一次插入，其余节点原样复用。

## 原理讲解

React Diff 的三条启发式规则：

1. **同层比较**：只比较同一层级的节点，跨层级移动直接重建；
2. **类型优先**：元素类型不同（如 `div` → `span`）直接卸载重建整棵子树；
3. **key 标识身份**：同一层级用 key 建立映射，key 相同则复用并按需移动，key 不存在则新建，多余的删除。

用 index 做 key 时身份与位置强绑定，位置一变身份就「错」了：

```text
旧: [A(idx0), B(idx1), C(idx2)]
新: [D(idx0), A(idx1), B(idx2), C(idx3)]

index 作 key：React 认为 idx0 变成 D、idx1 变成 A……全部原地更新 + 末尾新增，状态全错位
id 作 key：React 识别出 A/B/C 还在，只是位置后移，仅插入 D，DOM 与状态完美复用
```

**可以安全用 index 的场景**：纯静态列表——不会增删、不会排序、只读展示，且子项没有内部状态。此时 index 与 id 行为一致。

## 追问与易错点

- **key 要全局唯一吗？** 不需要，只要在**兄弟节点之间**唯一即可，不同列表之间可以重复。
- **能用 `Math.random()` 或 `index + item` 拼接当 key 吗？** `Math.random()` 每次渲染都变，等于告诉 React「全是新节点」，反而强制全部重建，比不写更糟。
- **key 能作为 props 传给组件吗？** 不能。key 被 React 内部消费，`props` 里拿不到；需要这个值就显式再传一个 prop（如 `id={todo.id}`）。
- **key 变化会怎样？** 同一个位置的元素 key 变了，React 视为不同节点：旧节点卸载、新节点挂载，内部 state 全部重置——有时也利用这一点做「重置组件」。
- **Vue 的 `v-for` key 机制一样吗？** 原理相通，都是给虚拟 DOM 节点提供身份标识以复用 DOM；Vue 同样不建议用 index 应对动态列表。
